# 企业内部多项目管理系统：项目启动与架构方案（交付 Codex）

> 文档用途：交给 Codex，在**全新且隔离的项目目录**中搭建可运行的第一版平台骨架；同时作为后续平台化迁移的产品与技术约束。  
> 方案版本：V1.0｜2026-10-22  
> 当前决策：**路线 A 优先——以 Horilla CRM 开源项目为基础做二次开发**。路线 B（Django + Unfold + 自定义业务 Apps）保留为验证失败后的备选，**本轮不并行实现两套系统**。  
> 工作方式：请先阅读旧仓库、核验新上游、提交评估，然后建设第一阶段可运行骨架；不要求一次做完完整 ERP、财务与续费迁移。

---

## 1. 项目目的及用户真正想要什么

本项目是公司内部使用的**多产品、多项目业务管理平台**，不是给现有“数智员工售后助手”继续堆功能。目标产品结构：

```text
企业总管理（统一入口、跨产品统计和待办）
  ├─ 项目/产品空间管理（选择进入某个业务空间）
  │    ├─ 数智员工（第一个正式业务空间）
  │    │    ├─ 项目概览与客户工作台
  │    │    ├─ 指令、服务部署、续费任务
  │    │    ├─ 项目合同、账单、应收与收款视图
  │    │    ├─ 技术资料、财务资料
  │    │    └─ 外部数据同步、企微通知与自动化
  │    └─ 未来其他产品/项目（现在仅设计可扩展入口，不虚构具体业务）
  ├─ 平台共享业务能力
  │    ├─ CRM / 客户及公司主体
  │    ├─ 订单、合同、账单、收款（逐步落地）
  │    ├─ 文件/资料管理、操作记录
  │    └─ 用户、角色、项目成员与授权
  └─ 独立的员工本机效率工具（后期独立 Windows Agent / EXE）
       └─ 浏览器 CDP、工具箱、JumpServer/VM、向日葵、屏幕取词
```

**核心规则**：

1. **总管理 → 项目分化管理**：登录先到全局经营/工作总览；点击项目卡片进入项目空间。平台共享能力与项目专属能力各归其位。
2. 总管理首页只展示真实、可比、可溯源的跨项目指标、项目卡片、待办和异常；不把所有项目各自的业务字段乱加成同一种 KPI。
3. 平台 CRM、财务、资料使用统一业务事实；项目内展示的是**有权限的本项目筛选视图**，不能做独立账本或重复客户主表。
4. 一个法人公司可能关联多个产品、多个客户账号、多个合同和多个 CID。**数智员工 CID 仅是来源系统的产品账号标识，不是整个平台通用的法人主键。**
5. 数智员工只是第一个产品空间；“壹号时光 / 迈诺特”等现有业务线先保留其当前业务含义，不因重构擅自升级为两个顶层产品空间。
6. 计划使用者约五人，部署在公司内部网络；优先简单、稳定、可维护。**模块化单体优先，不拆微服务、不做多租户 SaaS、不做复杂审批引擎**。如果选定的上游自带相关机制，应充分评估并最小化使用。
7. 黑白、暖灰、简约有质感的界面；继承当前客户工作台高频效率，避免为了统一 Horilla 风格而损失操作效率。

### 1.1 名词界定

- **平台**：公司内部管理系统整体。
- **业务空间（Workspace）**：一个产品线/独立业务项目的管理边界；前端可统一命名为“项目”，代码中可用 workspace 消除歧义。
- **产品线**：公司实际提供的产品。现阶段仅数智员工，之后可增加；产品线与独立客户交付项目不是必然一一对应。
- **共享主数据**：公司主体、联系人、用户、文件索引等，可被多个空间引用。
- **产品账号**：如数智员工来源系统 CID、账号、指令等。必须记录来源与映射，不能替代全局主数据。

## 2. 已选开源项目及研究优先级

### A. 本轮唯一建设底座：Horilla CRM

- 上游源码：https://github.com/horilla/horilla-crm
- 官方网站/文档：https://www.horilla.com/ ；https://docs.horilla.com/
- 已核查到的仓库结构（以实际 checkout 的源码为准，不要照抄文档）：
  - `horilla/`：平台内核，含 `contrib` 公共能力、`menu`、`registry`、`settings`、`urls`、认证、仪表盘等。
  - `horilla_crm/`：CRM 业务包，含 `accounts`、`contacts`、`leads`、`opportunities`、`campaigns` 等。
  - `horilla/settings/horilla_apps.py`：目前用 `INSTALLED_APPS.extend(...)` 扩展产品 Apps。
  - `horilla_crm/accounts/apps.py`：可借鉴 `AppLauncher`、`url_prefix`、`url_module`、`auto_import_modules` 注册模式。
  - `horilla_crm/accounts/menu.py`：可借鉴菜单注册及权限约束。
- 许可：仓库标注 LGPL-2.1+；二次开发保留版权与许可证，维护上游与自研代码边界；不要默认上游额外产品模块都已存在。
- **已发现版本文档不一致**：目前公开仓库 `requirements.txt` 指定 `Django==6.0.4`，部分 README/源码注释仍表述 Django 5.2。Codex 必须记录克隆时的 commit SHA、实际 Python/Django/依赖版本、测试结果；不能凭 README 猜环境，也不要自行任意降级/升级依赖。
- **注意上游迁移特殊情况**：README 提到从旧 v1.9 升级到 v1.10.0 时 app label 变化与 `sync_db` 操作；**本项目为全新数据库安装，不得对新库或旧 MagicTool 库贸然运行该历史升级工具**。
- **首要任务**：在全新测试环境先把上游按原样启动，确认登录、CRM 页面、权限、菜单、dashboard 及数据库迁移能正常工作，然后新增自研业务模块。禁止一开始大改上游内核。

### B. 若 A 经实际验证不合适，才讨论切换

- Django：https://github.com/django/django
- Django Unfold：https://github.com/unfoldadmin/django-unfold
- 备选设计：Django + Unfold + 自定义 `platform`、`workspaces`、`crm`、`finance`、`digital_employee` 等 Apps。
- **本轮不搭建路线 B**，但须在结项报告列出若放弃 Horilla 时可复用哪些本轮自研设计/数据契约。

### C. 仅作为业务能力/界面参考，不作为本轮集成底座

- BottleCRM（Django REST + SvelteKit）：https://github.com/Django-CRM/Django-CRM —— 参考简约 UI、CRM/订单/账单/工单流程；不可误把其组织多租户当成公司内部多产品空间。
- KoalixCRM：https://github.com/KoalixSwitzerland/koalixcrm —— 参考合同、发票、订阅等业务模型；须独立核对代码状态和许可。
- ERPNext：https://github.com/frappe/erpnext —— 参考账单、Payment Entry、收款核销；**不是 Django 插件**。
- Odoo：https://github.com/odoo/odoo —— 参考业务边界和模型；不是本次底座。

**选型不能仅凭“别人开源写的就一定比自研好”判断**。要比较实装结果：能复用哪些功能、上游耦合度、UI 定制量、升级难度、权限隔离和长期维护成本。Horilla 路线要经过明确的通过/退出判定（见第 9 节）。

## 3. 既有数智员工系统：Codex 必读、禁止凭空重建

旧系统仓库（只读研究）：https://github.com/YISHENG-D/magictool-helper

如本机存在旧目录，预期在 `E:\AAA-项目文件\MagicTool_helper`（**须实际核对，不得假定路径一定存在**）。重点阅读：

1. `README.md`：现有功能、启动方式、数据库/自动化边界。
2. `docs/当前进度.md`：**本次研究必须先读**，区分现行已发布、未发布、测试失败和仅规划内容。
3. `docs/产品设计.md`、`docs/数据设计.md`、`docs/公司内网多人访问验证.md`。
4. `magictool/web/`、`magictool/core/`、`magictool/storage/`、`magictool/assist/`：做业务与技术依赖盘点，不要求本轮代码迁移。

### 3.1 旧系统现有真实能力（用来制定迁移映射，而非第一期重做）

| 业务域 | 旧项目能力 | 新平台预定归属 |
|---|---|---|
| 客户工作台 | 按 CID 查询、搜索/筛选、客户详情、工具箱/系统/远程高频入口 | 数智员工专属工作台；共享客户主档另设映射 |
| 客户与服务器 | 管理系统来源客户、服务器、部署信息、VM/本地判断 | 数智员工来源账号与服务资源 |
| 指令中心 | 指令编号、名称、到期时间、产品类型、年费、套餐、客户专属报价 | 数智员工专属服务/产品规则 |
| 续费中心 | 30/15/7/0 提醒、月度排期、任务跟进、指令级不续费、登记/核验/撤销 | 数智员工专属业务工作流 |
| 续费账单 | XLSX 模板、价格快照、编号占用、防重复/并发修改、人工文件与生成文件唯一当前账单保护 | 数智员工账单生成；与共享应收模型关联但不混同 |
| 财务资料 | 合同/账单/水单/发票文件识别、关联、去重、人工确认归档 | 平台共享文件与财务业务；项目内限定范围 |
| 财务总览 | `/finance` 框架，真实金额统计尚未完全建立；不能把框架视为正式财务核销能力 | 共享财务模块逐步完善 |
| 公司主体 | CID 与法人主体关联在开发中，需要人工匹配、历史兼容 | 共享法人主档与数智员工账号映射 |
| 同步/提醒 | MagicTool 来源、工具箱、企微内部机器人、定时/手动摘要和回执 | 项目级数据集成 + 平台后台任务设施 |
| 本机效率工具 | pywebview、CDP、浏览器跳转、VM/JumpServer、向日葵、屏幕取词 | 独立 Windows Agent，后期可打包 EXE |
| 数据维护 | PostgreSQL 正式库 + Alembic；SQLite 测试/受控快照；备份/维护/版本校验 | 新平台使用**完全独立**数据库和迁移链 |

### 3.2 必须保留的旧业务事实边界

- 管理系统与工具箱同步数据有来源权威性，不可以用人工录入或新平台编辑随意覆盖来源事实；同步失败/0 条异常不可清空旧数据。
- 续费的“登记”“真实到期日更新”“工具箱核验通过”“人工确认续期”“不续费”相互有不同含义；不能用付款或账单生成自动判定已续费。
- 账单文件生成、财务应收、实际收款、收款核销、发送状态和续期结果是**不同业务事实**。
- 旧项目已有人工/生成账单编号、快照、唯一约束、资料文件校验和操作日志；迁移时不能简单使用 CSV 导入后覆盖或丢失关联。
- 公司主体、客户昵称、CID 不一定一一对应；法律主体的匹配要留人工确认与待核对状态。
- 当前旧系统没有成熟的全员账号/角色权限体系；新平台要补平台级登录及项目授权，同时防止敏感凭据被不合适的角色看到。
- 旧项目《当前进度》在 2026-10-21 仍记录了部分公司主体/财务迁移未发布、全量测试存在失败和 SQLite/PG 版本差异。**不得把文档中的任一 Alembic head 当作现场实时版本，后续数据迁移前必须实际只读核对。**

### 3.3 旧系统现状主要不是“没功能”，而是“分层不够明确”

Flask Web、续费和财务规则、共享数据库、Windows 桌面工具当前仍在一个大工程内。新系统应通过**统一平台基础 + 公共业务 Apps + 数智员工专属 Apps + 独立本机 Agent**建立清楚的依赖方向；不是把现有所有 Python 文件原样复制到 Horilla 里。

## 4. 新平台目标功能与导航

### 4.1 企业总管理（登录首页）

- 全局 KPI：在管产品/空间数、按法人去重的客户量、经确认的应收/实收/逾期、需要处理事项等。**首次骨架阶段无可信数据时显示 `—` / `待接入`，不可用随机假数伪装真实统计。**
- 项目卡片：名称、状态、关键指标、待办数量、最后同步/数据更新时间、进入项目按钮。第一项为“数智员工”；其他空间可显示“尚未接入”或使用测试数据明确标记。
- 全局待办、异常和跨项目快速入口；不复制各项目完整首页。
- 全局 CRM、财务、资料以权限内的统一数据视图为主，支持按项目/产品筛选。
- 一致的搜索、项目切换、通知入口、人员菜单、权限可见性。

### 4.2 数智员工项目空间（第一个业务空间）

- 项目概览、客户工作台、续费中心、指令中心、部署管理、项目财务、技术/财务资料、自动化/同步、项目设置。
- 第一阶段页面只实现**真实可用的导航、空状态和示例数据通道**，不要求复刻全部业务；后续可逐步迁入旧规则。
- 进入项目后顶部/侧栏始终显示当前空间及返回总管理入口；页面和 API 必须以项目权限限制数据范围，不能仅靠前端隐藏。
- 旧客户工作台的高频操作（客户详情、工具箱、远程等）应该通过定制页面保留，不强迫塞入 CRM 的标准编辑表单。

### 4.3 全局/项目导航建议

**平台：** 总览 / 项目中心 / 客户中心 / 财务中心 / 资料中心 / 平台管理。

**进入数智员工后：** 项目概览 / 客户工作台 / 续费中心 / 指令中心 / 部署管理 / 项目财务 / 项目资料 / 自动化管理。

不要求将所有模块一开始全部做成可用业务；对尚未接入的页面明确展示“建设中”及当前范围，不提供会误写真实数据的假操作按钮。

### 4.4 风格原则

- 偏高级感的经典黑白/暖灰，轻量低饱和状态色；空间适中，不堆无意义统计卡片和炫图表。
- 参考 BottleCRM 的清晰文字侧栏、分组与留白，参考 Horilla 可配置看板和模块扩展能力。
- 总览强调决策信息，项目首页强调高频工作入口；宽屏 1920×1080 下内容密度合理、无水平溢出；小屏可滚动或折叠导航。
- 复用上游组件、主题和图表机制；**不要为了换皮把 Horilla 全部 CSS/JS 重写**。

## 5. 初步目标架构（实现细节由 Codex 在上游验证后决定）

### 5.1 模块化单体，不做多租户 SaaS

- 基础：Horilla 自带 Django 平台服务、登录、菜单注册、权限、基础 CRM、dashboard、API 等（以实测可用项为准）。
- 自研公共包（建议命名 `company_platform/`，允许经验证后调整）：workspace、跨项目看板、公共客户映射、共享业务入口、权限范围、项目成员。
- 自研业务包（建议命名 `digital_employee/`）：后期封装已有数智员工客户、指令、续费、部署、文件、同步适配器等业务，不要求第一阶段迁移全量。
- 不在第一阶段引入新的微服务或消息中间件；如 Horilla 自带 Celery/Channels/Redis 等，按实际必需依赖启用并记录成本。
- 数据库：新项目专用 PostgreSQL 实例或独立 database/user；数据库隔离第一，不能复用 MagicTool 正式库的 schema 或迁移版本表。
- 文件存储：测试独立 `media`，以后再设计共享文件和历史文件映射，不得直接读写旧项目正式文件目录。
- 本机 Agent：**与 Web/后台服务器完全分开**，后期在员工 Windows 电脑执行。客户端发起且完成身份验证/授权后再执行本地操作；服务器不得直接操作自己那台机器来冒充客户端跳转成功。

### 5.2 源码管理与上游升级

推荐从 Horilla CRM 上游克隆到独立目录，并将 `upstream` 记录为官方仓库；自研功能尽量放在独立包，明确自定义配置入口。Codex 应先查清如何注册自定义 `AppLauncher`、菜单、仪表盘及 URL，优先最小扩展，避免直接 fork/修改大量 `horilla/contrib` 代码。

目标结构示意（**不是要求一比一照此创建所有空文件**）：

```text
企业内部多项目管理系统/
  horilla/                  # 上游平台代码，尽量少改
  horilla_crm/              # 上游 CRM 产品包，按需启用
  company_platform/         # 新增：总管理、业务空间、公共集成能力
  digital_employee/         # 新增：数智员工产品模块（首期入口/空状态）
  docs/
    00-项目目标与边界.md
    01-上游验证与技术决策.md
    02-旧项目功能迁移矩阵.md
    03-开发运行与验收.md
  .env.example              # 仅模板；绝不放真实密钥
  README.md
  ...                       # Horilla 上游原有文件保持
```

### 5.3 数据概念（先写设计，不在第一阶段接管旧业务表）

- `Workspace`：业务空间标识、名称、状态、类型、显示排序、默认首页、业务指标配置。
- `WorkspaceMembership`：人员与空间、角色/权限，含禁用与审计信息。
- `LegalEntity/Company`：平台法律主体/客户主档；优先确认能否以 Horilla `Account` 承载，**不要再平行建第二份客户主表**。
- `ExternalCustomerAccount`：空间、源系统、CID/账号与平台主体的映射，可待确认，需考虑唯一性与历史。
- `Order/Contract/Invoice/Receivable/Payment/Allocation`：逐步复用或扩充已有 CRM/财务模型，不要求本期建全套。正式应收/核销状态、收款流水和附件要分开。
- `SourceSyncRun / OperationAudit`：与既有来源同步和操作日志的关系，后续再落库设计。

上述只是**概念实体**，请先盘点 Horilla 实际模型与唯一约束，再写最终建模方案；不要为了形式一次新建大量与上游重叠的表。

## 9. 技术风险、停止条件与路线 B 判定

### 必查风险

- Horilla 上游可能正在快速调整应用标签、菜单和数据库迁移；选定 commit 必须固定，并且建立上游同步评估流程。
- README、requirements 与实际代码版本可能冲突；以**测试过的源码+锁定依赖**为准。
- Horilla 平台 CRM 功能丰富，但不代表合同、月结、收款、财务核销已完整存在。
- Horilla 可能已拥有 company/org 作用域；不要把“同公司多个产品”误建成不同租户或者重复客户库。平台角色、CRM 权限和项目角色应有清楚的边界。
- 长期维护可能被上游私有设计/强耦合绑死；记录每一处修改上游内核的必要性和替代方案。
- 旧系统 Windows 本地浏览器/远程自动化不能直接迁为服务端执行，否则多机用户点击动作会在服务器上发生。
- 财务数据不能未经核实便显示汇总；订单、账单、收款、核销和续期状态相互独立；要有日志、权限和不可随意覆盖的修正机制。

### 评估不通过时的处理

若出现下列情况之一，**停止继续深入集成，形成证据报告交用户决策**，不要自行直接切换 Django+Unfold：

1. 原版 Horilla 在可接受的测试环境中无法稳定启动或关键迁移失败，且需大范围修改核心源码。
2. 自定义项目空间接入必须修改大量上游内部代码，后续升级代价明显高于自建 Django Apps。
3. 无法建立可靠的平台权限与项目隔离（存在越权访问或数据串读）。
4. 引入的后台服务与依赖明显超出小团队实际维护能力，且不能合理精简。

届时提供“Horilla 可行性结论 + 问题清单 + 已完成可保留资产 + Django/Unfold 备选估算”，由用户再决定是否执行路线 B。
