# Horilla CRM 项目评估报告

## 1. 评估基本信息

- 评估对象：Horilla CRM 开源平台
- 原始项目目录：`E:\AAA-项目文件\horilla-crm`
- 评估日期：2026 年 10 月 23 日
- 评估目标：判断 Horilla 是否适合作为企业内部多项目管理系统的基础平台
- 本轮范围：源码结构、运行环境、数据库隔离、核心功能、扩展边界和后续建设可行性
- 明确不在本轮范围内：正式业务数据迁移、MagicTool Helper 修改、真实外部同步、真实邮件或消息发送

## 2. 结论摘要

Horilla CRM 可以作为企业内部多项目管理系统的业务底座，适合采用“保留 Horilla 核心、在其上增加企业项目管理模块”的建设路线。

本次评估未发现必须放弃 Horilla、改用全新 Django 项目或切换到 Django + Unfold 的架构性问题。Horilla 已具备 Django 项目基础、用户与权限体系、CRM 业务对象、后台管理能力以及可继续扩展的应用结构。

但 Horilla 本身不是完整的企业多项目管理系统。项目空间、项目组合、项目成员、项目角色、里程碑、任务协作、企业级数据隔离和数智员工等能力仍需要作为新的业务模块建设，不能仅通过配置现有 CRM 菜单完成。

## 3. 已完成的验证工作

### 3.1 独立环境验证

已在原 Horilla clone 目录中使用独立环境进行验证，未依赖 MagicTool Helper 的运行环境和数据库。

已验证内容包括：

- 独立 Python 虚拟环境；
- 独立 SQLite 验证数据库 `horilla-validation.sqlite3`；
- Django 数据库迁移；
- `manage.py check` 检查；
- Horilla 核心测试；
- 本地开发服务启动；
- 浏览器登录和首页访问；
- CRM 示例数据展示。

### 3.2 测试结果

本次已完成的核心测试共 48 项，结果为通过。数据库迁移和 Django 系统检查未发现阻塞性错误，浏览器可以正常访问本地 Horilla 页面并完成登录验收。

验证使用的是独立测试数据库，不涉及正式业务数据库，也未修改原 MagicTool Helper 项目。

### 3.3 浏览器验收结果

已验证以下基本流程：

1. 启动本地开发服务；
2. 打开 Horilla 登录页面；
3. 使用测试账号登录；
4. 进入系统首页；
5. 查看 CRM 相关页面和示例数据；
6. 验证页面路由和基础静态资源加载。

## 4. Horilla 现有能力评估

### 4.1 可直接复用的能力

Horilla 可以直接作为以下基础能力的承载平台：

- Django Web 应用基础；
- 用户、登录和会话管理；
- 权限与角色控制基础；
- CRM 客户、联系人、线索等业务对象；
- 列表、表单、详情页和基础筛选交互；
- 数据库迁移和模型管理机制；
- 后台任务和应用模块组织方式；
- 基础系统菜单和页面布局；
- SQLite 开发验证和后续生产数据库扩展路径。

### 4.2 不能直接等同于项目管理系统的部分

以下能力不能假设 Horilla 已经完整提供：

- 企业总管理首页；
- 多项目空间切换；
- 项目组合和项目层级；
- 项目成员与项目角色；
- 项目任务、里程碑和依赖关系；
- 项目级权限和数据隔离；
- 跨项目统计和经营分析；
- 数智员工任务编排和执行记录；
- 与原 MagicTool Helper 的业务数据兼容；
- 外部系统同步、通知和消息发送。

这些能力需要通过新的 Django App、模型、URL、菜单、权限和前端页面逐步建设。

## 5. 推荐的扩展边界

建议保持 Horilla 核心代码相对稳定，将企业内部能力放在独立应用中。建议后续按业务边界拆分为以下模块：

```text
project_management/
enterprise_platform/
digital_employee/
```

具体模块名称可以根据实际代码结构调整，不要求机械采用上述目录名称。

第一阶段建议建立以下核心模型：

```text
ProjectSpace
Project
ProjectMember
ProjectRole
ProjectTask
ProjectMilestone
```

模型设计应优先考虑：

- 公司或组织归属；
- 项目空间归属；
- 用户和成员关系；
- 项目级权限；
- 任务状态和负责人；
- 审计字段；
- 后续跨项目统计需要的时间和状态字段。

## 6. 建设可行性判断

### 6.1 可行部分

Horilla 适合作为本项目的底座，原因如下：

1. 已经具备可运行的 Django 工程结构；
2. 用户登录、权限和业务页面模式可以复用；
3. CRM 数据模型能够支撑客户和组织相关业务；
4. 新业务可以以独立 Django App 方式接入；
5. 本地开发、测试数据库和正式数据库可以隔离；
6. 不需要为了增加项目管理能力而重写整个系统。

### 6.2 需要重点控制的部分

#### 数据隔离

不能只依赖页面上的筛选条件实现项目隔离。项目级数据访问必须在查询层、权限层和服务层同时控制，避免用户通过接口或参数访问其他项目的数据。

#### 权限模型

Horilla 现有权限能力可以作为基础，但项目角色、项目成员和公司管理权限之间需要重新定义，不能直接把系统管理员权限等同于项目负责人权限。

#### 核心代码升级冲突

如果直接大量修改 Horilla 核心模板、核心模型或核心视图，后续同步官方更新的成本会明显增加。应优先采用新增 App、扩展菜单、继承模板和局部覆盖的方式。

#### 外部集成

当前阶段不应启动真实同步和消息发送。外部集成应先定义接口、日志、重试、幂等和失败处理，再使用测试环境验证。

#### 数据迁移

原 MagicTool Helper 的数据结构和 Horilla 的数据结构不能默认兼容。正式迁移前需要完成字段映射、主键策略、重复数据处理、权限映射和回滚方案设计。

## 7. 当前 Git 与项目组织建议

推荐以 Horilla 源码作为主项目，而不是把完整 Horilla 目录嵌套到另一个旧项目中。

建议结构：

```text
enterprise-management-platform-horilla/
├─ horilla/
├─ horilla_crm/
├─ manage.py
├─ requirements.txt
├─ project_management/       # 后续新增
├─ enterprise_platform/      # 后续新增
├─ digital_employee/        # 后续新增
└─ docs/
```

原 Horilla 的提交历史可以保留。自己的 GitHub 仓库应作为 `origin`，官方仓库是否配置为 `upstream` 取决于后续是否需要同步官方更新。

如果目标是完全独立的 GitHub 仓库，应在 GitHub 新建空仓库后推送，而不是继续使用原 Fork 仓库作为最终项目仓库。

## 8. 当前未完成事项

以下内容尚未完成，不应将当前项目称为完整的企业多项目管理系统：

- 企业总管理首页的正式实现；
- 项目空间切换；
- 项目、成员、角色和任务模型；
- 项目级权限和数据隔离；
- 数智员工模块骨架；
- 项目管理页面和导航菜单；
- 跨项目报表和经营指标；
- 原 MagicTool Helper 数据迁移；
- 外部同步和消息通知；
- 生产部署和安全加固；
- 完整的浏览器自动化回归测试。

## 9. 下一阶段建议

建议按照以下顺序继续建设：

### P0：平台和边界确认

- 固定 Horilla 版本和分支；
- 固定本地开发环境；
- 形成独立测试数据库；
- 确定新 App 的命名和目录边界；
- 明确公司、项目空间、项目和用户之间的关系；
- 建立基础测试账号和测试数据规范。

### P1：最小可运行业务骨架

- 新建项目管理 App；
- 建立项目空间和项目模型；
- 建立成员和角色模型；
- 实现项目空间切换；
- 实现项目列表、项目详情和基础任务页面；
- 增加企业总管理首页骨架；
- 增加数智员工模块入口和基础状态页面；
- 建立模型测试、权限测试和浏览器验收测试。

### P2：业务完善和迁移准备

- 完善项目任务、里程碑和统计；
- 增加跨项目管理视图；
- 增加审计和操作日志；
- 设计 MagicTool Helper 数据映射；
- 在脱敏测试数据上验证迁移；
- 设计外部同步接口和失败重试机制；
- 完成部署、备份、权限和安全检查。

## 10. 最终评估结论

Horilla CRM 当前可以作为本企业内部多项目管理系统的建设基础，建议继续采用 Horilla 作为主平台，并通过独立 Django App 扩展项目管理和数智员工能力。

本阶段最重要的原则是：保留 Horilla 核心能力、控制核心修改范围、先完成项目空间和权限模型、使用独立测试数据验证，不提前迁移正式业务数据或启用真实外部同步。

在完成 P1 的最小业务骨架并通过权限和浏览器验收后，再决定是否进入正式数据迁移和外部系统集成阶段。
